# vast-4090-151594: RTX 4090 x1, Japan (Vast machine 151594, spot)

Ada, compute 8.9, driver 580.178.04, 500 W power limit, max SM clock 3150 MHz. v0.5.12
release, one miner. The release core on Ada is cu12.

nvidia-smi reports a 500 W limit, but the card drew 392-398 W in every sample while its clock
moved between 2415 and 2490 MHz (76-78 C). Power that stays flat while the clock moves looks
like a cap near 400 W that `power.limit` doesn't show, though heat or voltage could also be
the limit. The `[gpu]` line can't tell these apart; `enforced.power.limit` and
`clocks_event_reasons.active` would.

## The box was destroyed at 09:14

The supervisor destroyed instance 54811464 at 09:14:07 after two unprofitable checks in a
row (09:02 and 09:14). Both read the orphan-era `[mining]` lines, which showed one of two
miners at 138-141 TH/s, not the box's real rate. The main session's reboot at 09:12 had

## Memory clock lock on Vast

The 5090 in Maryland (151626) and the L40S in South Africa (149491) show the same: the CLI's default 7001 MHz lock leaves it at
mem=13801. So `--mine-mem-clock` does nothing on these Vast boxes, and the 5090 default is not
in effect on them either.

## Stopped at 09:44

The box was not re-rented within 30 minutes of being destroyed. `rewatch.py` only re-rents
boxes whose outcome starts with "released", and this one's is "stopped: unprofitable", so it
won't come back unless the main session rents it again. No test ran cleanly here, so there
is no verified gain. The control file is back on the release default, so a new rental
starts and stays on it with no restart.
