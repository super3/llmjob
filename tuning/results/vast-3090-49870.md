# vast-3090-49870: 8x RTX 3090, Bulgaria (machine 49870)

Driver 570.195.03, so the release CLI loads its CUDA 12.8 core (`release` = `cu12`). The CUDA 13
core has no sm_86 code, so there is no cu12-vs-cu13 test on this card. 350 W cap, 6 MB L2,
GDDR6X at 9501 MHz.

The cards are power-limited: 343-349 W of 350 on seven GPUs, SM clock 1530-1635 MHz (max 2100),
65-78 C. g6 is the odd one: 308 W at 1485 MHz, so something other than power holds it back.
Per clock the fold already runs about 95% of the int8 tensor peak (82 SMs x 1024 MAC a clock),
so only energy per MAC can raise the rate here.

## Where it ended

Best verified settings: the release default on all eight GPUs (no change beat it). The revert
was pushed at 11:09, but the box stopped at about 11:08, when the Vast account ran out of credit
(the supervisor's rebids failed with `insufficient_credit`), and it was released at 11:28. So
if this instance's disk ever resumed, g1/g5 would run f32/f63 for one control fetch (about 2
minutes) before switching back to the release.

The control file is all-release (`gpus {}`), with four builds queued at df0fb5c so a re-rent
compiles them (about 12 s each for sm_86) and a later agent can start at once:
f63 and f32 (operand fill, done above), and cb1024 and cb256 (`-DPEARL_AMPERE_COL_BATCH`).
The next test I'd run: cb1024 on g1 and cb256 on g5 against the release, after a fresh
baseline. Ampere's 512 was picked on a 300 W 3090, and on a 48 MB Ada card the batch width
mattered more than the L2 model said. Expect well under 1% here, since by the same reasoning
DRAM traffic per MAC on a 6 MB L2 hardly changes with the width.

Things the harness can't show that would help on this card: `clocks_event_reasons.active` and
`enforced.power.limit` in the `[gpu]` line, to see what holds g2 and g6 under the cap.
